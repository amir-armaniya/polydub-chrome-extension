## ۱. چشمانداز و محدوده این سند

**PolyDub** اکستنشن کرومی است که با Google Gemini صفحات، ویدیوها و پادکست‌ها را به فارسی ترجمه و دوبله می‌کند. این سند الزامات کامل فازهای **۳ تا ۶** را تعریف می‌کند (فازهای ۰–۲ در کد پیاده‌سازی شده‌اند):

| فاز | عنوان | وضعیت |
|---|---|---|
| ۰ | اسکافلد پروژه | ✅ کامل (tags: `phase0-checkpoint`) |
| ۱ | ترجمه متن صفحه | ✅ کامل (tags: `phase1-checkpoint`) |
| ۲ | خواندن متن انتخاب‌شده با TTS | ✅ کامل (tags: `phase2-checkpoint`؛ صف پخش + بازخورد ترجمه) |
| **۳** | **خواندن متن ترجمه‌شده صفحه** | ⬜ این سند |
| **۴** | **دوبله زنده ویدیو/پادکست** | ⬜ این سند |
| **۵** | **حالت پادکست (پخش فقط-صدا با پیشرفت و ادامه‌دهی)** | ⬜ این سند |
| **۶** | **تعویض خودکار صدا بر اساس گوینده** | ⬜ این سند |

**قانون غیرقابل‌مذاکره پروژه (از فاز ۰):** هر فاز هم **تست کد** (`npm test` + `npm run typecheck` + `npm run build`) و هم **تست واقعی** (بارگذاری در کروم واقعی، پورت CDP 9257، پروفایل `/tmp/opencode/ui-test`، پروکسی `127.0.0.1:10808`، بررسی صفحه خطاهای `chrome://extensions/?errors=…`) را می‌طلبد. پس از هر build، اکستنشن باید دستی Refresh شود.

## ۲. اصول و تصمیمات مشترک (Cross-cutting)

اینها در تمام فازهای ۳–۶ حاکم‌اند:

### ۲.۱ مدل‌ها
| کار | مدل | یادداشت |
|---|---|---|
| ترجمه متن | `gemini-3.1-flash-lite` | تأییدشده در فاز ۱؛ ارزان‌ترین، Stable |
| TTS | `gemini-3.1-flash-tts-preview` | ۲۴kHz/16bit/mono PCM (خروجی `audio/l16`، باید به WAV تبدیل شود)؛ استریم فقط از 3.1 به بعد (`streamGenerateContent` SSE)؛ پنجره کانتکست ۳۲K توکن؛ بدون cache |
| دوبله زنده (گزینه آینده) | `gemini-3.5-live-translate-preview` | گفتار→گفتار؛ ورودی PCM 16kHz، خروجی 24kHz؛ نیازمند ephemeral token از سرور (v1alpha) → وابستگی بک‌اند (خارج از محدوده ۳–۶) |
| ASR/رونویسی | مدل متنی با ورودی صوتی (`gemini-3.1-flash-lite`) | استخراج متن از صدای ویدیو/پادکست |

### ۲.۲ هزینه (قیمت‌گذاری رسمی ۲۰۲۶-۰۸)
| مدل | ورودی | خروجی | هزینه تقریبی استفاده |
|---|---|---|---|
| 3.1 Flash TTS | رایگان (Free Tier) / $1.00 هر ۱M توکن | رایگان (Free Tier) / $20.00 هر ۱M توکن صوتی | ~$1.8 در ساعت صدا (۲۵ توکن صوتی/ثانیه) |
| 3.5 Live Translate | رایگان / $3.50 هر ۱M | رایگان / $21.00 هر ۱M | ~$0.037 در دقیقه |
| Flash-Lite (ترجمه/ASR) | $0.25 هر ۱M | $1.50 هر ۱M | ناچیز |

> تصمیم: در همه‌جا از Free Tier استفاده می‌شود؛ اگر سهمیه پر شد، خطای دوستانه + پیشنهاد تنظیم voice و کاهش دوبله.

### ۲.۳ امنیت و حریم خصوصی
- کلید API فقط در `chrome.storage.local`؛ هرگز در کد/commit.
- هیچ داده صوتی و متنی به‌جز کش متن ترجمه (سقف ۲۰۰۰ مدخل) و پیشرفت پادکست (متن‌شده) در storage نمی‌نشیند؛ **صوتی ذخیره نمی‌شود** (حجم و حریم خصوصی).
- مسیر Live API (اگر در آینده) هرگز کلید را در درخواست‌های کلاینت نگذارد؛ نیازمند سرور ephemeral token → به صراحت **خارج از محدوده** فازهای ۳–۶ مگر تصمیم‌گیری جدید.
- CSP استریم SSE در SW مجاز است (fetch stream در service worker بدون تغییر CSP کار می‌کند؛ تأیید در تست واقعی).

### ۲.۴ عملکرد (بودجه)
- شروع پخش Read ≤ ۳ ثانیه (جمله اول) و بدون گپ بین جملات (pipeline).
- دوبله زنده: تأخیر سرتاسری هدف ≤ ۲.۵ ثانیه (شکستنی، در ریسک‌ها).
- حافظه صف پخش: حداکثر ۵۰ کلیپ در حافظه؛ قدیمی‌ترین پخش‌شده حذف شود.
- بیدارشدن SW < ۵۰۰ms.

## ۳. فاز ۳ — خواندن متن ترجمه‌شده صفحه (Read Translated Page)

### ۳.۱ هدف
بعد از ترجمه صفحه به فارسی، کاربر بتواند **کل متن ترجمه‌شده صفحه را پیوسته بشنود** (نه فقط انتخاب)؛ همان تجربه «پادکستِ صفحه». پایه‌اش صف پخش فاز ۲ است.

### ۳.۲ داستان کاربر
- پس از Translate Page، در تب Read دکمه **Read Page** فعال می‌شود؛ با کلیک، جمله به جمله فارسی خوانده می‌شود بدون گپ.
- جمله‌ای که در حال خوانده شدن است روی صفحه **هایلایت ظریف** می‌شود (و در صورت نیاز به دید، اسکرول می‌شود).
- کنترل‌ها: Play/Pause، Stop (مکث با حفظ صف)، Clear (پاک‌سازی کامل صف) — مطابق اسپک فاز ۲.
- با Revert Page پخش فوراً متوقف و صف پاک می‌شود.
- اگر متنی ترجمه نشده باشد: دکمه غیرفعال با راهنمای «First translate the page».

### ۳.۳ الزامات عملکردی
1. **جمع‌آوری متن:** content script از وضعیت ترجمه (`state.originals`) متن‌های ترجمه‌شده را استخراج کند (نه از DOM زنده که ممکن است جا به جا باشد)؛ پیام `polydub-get-translated-text` با پاسخ `{ sentences: string[] }`.
2. **تقسیم جمله:** همان `splitIntoSentences` فاز ۲ (نشانه‌های `. ! ? ؛ ؟ \n`).
3. **پایپ‌لاین سنتز:** SW جمله‌به‌جمله سنتز می‌کند؛ سنتز جمله i+1 هم‌زمان با پخش i؛ اولین صدا ≤۳ ثانیه.
4. **صف پخش:** offscreen طبق فاز ۲ (Play/Pause/Stop/Clear)؛ رویداد `ended` → جمله بعد.
5. **هایلایت جمله:** content script با پیام `polydub-highlight-sentence {index}` جمله فعلی را نشانه‌گذاری می‌کند (کلاس CSS ظریف + `scrollIntoView({block:'nearest'})`)؛ با پایان پخش حذف.
6. **کش صوتی جلسه‌ای:** برای جلوگیری از سنتز دوباره هنگام پخش مجدد، کلیپ‌های سنتز شده در **حافظه SW** (Map با کلید hash متن) نگهداری می‌شوند؛ **در chrome.storage ذخیره نمی‌شوند** (سهمیه).
7. **توقف‌ها:** Revert → پیام `polydub-audio-command {command:'clear-queue'}`؛ تغییر تب (visibility) پخش را متوقف نمی‌کند.
8. **خطا:** جمله خطادار رد می‌شود و جمله بعد پخش می‌شود؛ بعد از ۵ خطای متوالی متوقف با پیام «TTS failed — check your key and proxy».

### ۳.۴ الزامات غیرعملکردی
- حافظه: صف ≤ ۵۰ کلیپ؛ هایلایت بدون تغییر layout (کلاس `outline`، نه margin/padding).
- یکپارچگی: اجرای هم‌زمان Read Page و Read Selection مجاز نیست — انتخاب جدید صف قبلی را Clear می‌کند.
- RTL: هایلایت و اسکرول در صفحات فارسی درست کار کند.

### ۳.۵ معماری و جریان داده
```
popup (Read tab) ──polydub-read-page──▶ SW
  content: polydub-get-translated-text ◀──/──▶ (state.originals → sentences)
SW: splitIntoSentences → for each: synthesizeSpeech (pipeline) → polydub-play-audio {dataUrl}
offscreen: queue → play → ended → next → polydub-audio-state-update {sentenceIndex}
content: polydub-highlight-sentence {index} (هایلایت)
```

### ۳.۶ تست
- **واحد:** استخراج sentences از ساختار state (با/بدون متن خالی)؛ یکپارچگی splitIntoSentences؛ منطق صف (Stop/Resume/Clear)؛ رفتار pipeline (سنتز بعدی قبل از پایان قبلی — با fake timers)؛ پایان پخش → هایلایت آخر حذف.
- **واقعی:** ترجمه example.com → Read Page → شنیدن فارسی (پروکسی فعال) → Pause/Resume/Stop/Clear → Revert → توقف خودکار → صفحه errors صفر.

### ۳.۷ معیارهای پذیرش
- [ ] شروع پخش ≤ ۳ ثانیه پس از کلیک؛ بدون گپ محسوس بین جملات
- [ ] هایلایت جمله فعلی روی صفحه و حذف آن در پایان
- [ ] Revert در حین پخش → توقف و پاک‌سازی فوری
- [ ] پخش مجدد همان صفحه بدون سنتز دوباره (کش جلسه‌ای)
- [ ] ۲۹+ تست واحد سبز، typecheck و build پاک، صفحه errors صفر

### ۳.۸ خارج از محدوده
هایلایت کلمه‌به‌کلمه (karaoke)، سرعت خواندن، ذخیره صوتی، چند زبان.

## ۴. فاز ۴ — دوبله زنده ویدیو/پادکست (Live Dubbing)

### ۴.۱ هدف
کاربر ویدیو یا صوتی را در تب فعلی پخش می‌کند؛ PolyDub در لحظه صدای اصلی را با دوبله فارسی **هم‌زمان** جایگزین می‌کند. قلب محصول و نقطه تمایز «live» در نام.

### ۴.۲ معماری پیشنهادی (دو گزینه، یکی انتخاب می‌شود)
**گزینه A (پیشنهاد): خط لوله چندمرحله‌ای Capture → ASR → Translate → Streaming TTS**
1. `chrome.tabCapture` صدای تب را می‌گیرد (PCM، نیازی به دسترسی به عنصر رسانه؛ با سایت‌های ویدیویی هم کار می‌کند).
2. خوشه‌بندی صدا (chunk 0.5–۲ ثانیه) + VAD (حذف سکوت/موسیقی‌محض؛ آستانه ساده انرژی) در offscreen.
3. ASR: هر خوشه با Gemini (ورودی صوتی) به متن تبدیل می‌شود.
4. ترجمه: `translateItems` موجود (حالت پای‌لاین با onProgress).
5. TTS استریم: `streamGenerateContent` با `responseModalities:["AUDIO"]` → دیکد افزایشی PCM 24kHz → WAV per chunk → صف پخش.
6. پخش دوبله روی ویدیو: خروجی offscreen؛ صدای اصلی با `tabCapture` mute می‌شود؛ بافر تأخیر + اصلاح رانش (drift).

مزایا: بدون بک‌اند؛ همه قطعات موجود (translate + tts + queue)؛ کنترل کامل؛ قابل توسعه به فاز ۵/۶.
معایب: ۳ مرحله API → تأخیر بالاتر (۲–۳.۵ ثانیه)؛ پیچیدگی هماهنگی.

**گزینه B: Live API گفتار→گفتار (`gemini-3.5-live-translate-preview`)**
مزایا: تأخیر ~۱ ثانیه؛ سادگی منطق. معایب: **نیاز به سرور ephemeral token** (کلید در کلاینت درز می‌کند) → وابستگی بک‌اند؛ محدودیت پیش‌نمایش (rate limit)؛ زنجیره صوتی از پیش تنظیم شده (کنترل صدا/تأخیر کم).

> **تصمیم این PRD: گزینه A.** گزینه B به‌عنوان ارتقای آینده (پس از فاز ۶) ثبت می‌شود؛ معماری صف فاز ۲ طوری طراحی شده که سمت پخش بعداً به دیکدر استریم سوئیچ شود بدون تغییر رابط صف.

### ۴.۳ داستان کاربر
- در تب Live (نام جدید تب: **Dub** با دو حالت Live و Podcast — تصمیم UX در ۴.۵) دکمه **Start Dubbing** → صدای تب گرفته می‌شود؛ وضعیت «Listening… / Translating… / Playing» نمایش داده می‌شود.
- با شروع دوبله، صدای اصلی بی‌صدا و دوبله فارسی پخش می‌شود؛ ویدیو همان‌طور ادامه دارد.
- کنترل: Stop (قطع کامل و برگشت صدای اصلی)، تأخیر دستی (±100ms)، Mute/Unmute صدای اصلی، انتخاب voice و زبان هدف (fa پیش‌فرض، فارسی در UI سند).
- اگر تب بدون صدا باشد یا capture رد شود: پیام واضح «No audio detected in this tab».

### ۴.۴ الزامات عملکردی
1. **Capture:** `chrome.tabCapture.capture({audio:true, video:false})` در بازه جلسه دوبله؛ جریان به offscreen منتقل شود؛ در Stop آزاد شود (limit: تب متوقف/تغییر → توقف خودکار).
2. **VAD/خوشه‌بندی:** خوشه‌های گفتار پیوسته (سکوت >400ms جداکننده)؛ آستانه انرژی قابل تنظیم (Settings → `vadThreshold`)؛ خوشه‌ها سقف ۳۰ ثانیه (شکستن برای token limit).
3. **ASR:** پرامپت: «Transcribe Persian/English speech exactly. Return text only.» خروجی متن → ترجمه. در صورت خالی/موسیقی → skip.
4. **Streaming TTS:** استریم SSE؛ هر event دلتا PCM → تبدیل به کلیپ WAV قابل پخش؛ تا ۵۰ کلیپ صف (فاز ۲).
5. **هماهنگی:** بافر اولیه ۵۰۰ms قبل از شروع پخش؛ اصلاح رانش با افزودن/حذف سکوت کوتاه بین کلیپ‌ها (در offscreen)؛ seek کاربر به عقب → از جایی که capture می‌کند، دوباره سازگار می‌شود (چیزی که از دست رفته خوانده نمی‌شود — اعلام شفاف در UI؟ خیر، پیش‌فرض بی‌صدا ادامه).
6. **توقف:** Stop → استریم بسته، صف پاک، صدای اصلی برگردد، دکمه دوباره «Start Dubbing».
7. **خطاها:** خطای ASR/TTS خوشه → skip خوشه و ادامه (حداکثر ۵ متوالی → توقف با پیام)؛ قطع شبکه (پروکسی) → تلاش مجدد ۲ بار با backoff.

### ۴.۵ UX و UI
- تب فعلی «Live Dub» به **Dub** تغییر نام می‌دهد با دو بخش: **Live** و **Podcast** (پایپایپ فاز ۵ همین‌جا).
- پنل Live: دکمه بزرگ Start/Stop، نشانگر وضعیت سه‌حالته، نمایشگر تأخیر تقریبی (ms)، اسلایدر تأخیر، Toggle mute اصلی، انتخاب voice.
- بدج در آیکون اکستنشن: حین دوبله، نشانگر قرمز (badge «●») — در فاز ۴ الزامی نیست (خارج از محدوده اگر پیچیده شد: تصمیم در اجرا).

### ۴.۶ الزامات غیرعملکردی
- تأخیر هدف ≤ ۲.۵ ثانیه (بسته به پروکسی؛ بودجه تلاش، نه تضمین).
- مصرف: فقط یک جلسه دوبله هم‌زمان؛ capture آزاد در Stop.
- سازگاری: بدون کد مخصوص سایت (YouTube و غیره همه از capture رد می‌شوند).

### ۴.۷ تست
- **واحد:** خوشه‌بندی/VAD با آرایه PCM ساختگی؛ مونتاژ استریم PCM→WAV؛ منطق رانش (سکوت‌گذاری)؛ skip-after-5-errors؛ آزادسازی capture در مسیرهای خطا (mock).
- **واقعی:** پخش یک ویدیوی کوتاه با صدای انگلیسی در تب (proxied) → Start Dubbing → شنیدن دوبله فارسی ~۲–۳ ثانیه بعد → mute/بازگشت صدا → Stop → صفحه errors صفر.

### ۴.۸ معیارهای پذیرش
- [ ] دوبله گفتار انگلیسی ساده ویدیو به فارسی با تأخیر ≤ ۳.۵ ثانیه در شرایط عادی
- [ ] توقف/استارت بدون نشتی capture و بدون پخش هم‌زمان دو صدا
- [ ] خطای خوشه، جریان را نمی‌شکند
- [ ] تست‌های واحد جدید + رگرسیون کامل سبز؛ تست واقعی تأییدشده

### ۴.۹ خارج از محدوده
سازگاری با seek به عقب (بازپخش دوبله)، زیرنویس، چند تب هم‌زمان، Live API (گزینه B)، صداهای چندگوینده (فاز ۶).

## ۵. فاز ۵ — حالت پادکست (پخش ترجمه‌شده فقط-صدا)

### ۵.۱ هدف
برای **صوتی‌ها (پادکست)**: کاربر «Dub Episode» می‌زند؛ کل اپیزود رونویسی → ترجمه → دوبله می‌شود و با کنترل پخش کامل (پیشرفت، ادامه‌دهی، سرعت) شنیده می‌شود. تفاوت با فاز ۴: فاز ۴ بلادرنگ (گذر-لحظه) است؛ فاز ۵ یک جریان کاری عمدی با **کیفیت و ثبات ترجمه بهتر** (ترجمه با کانتکست بخش‌ها) و **قابلیت ادامه** است.

### ۵.۲ داستان کاربر
- در صفحه‌ای با `<audio>`/پخش‌کننده صوتی → «Dub Episode» → رونویسی شروع می‌شود («Transcribing… 12%»).
- پس از آماده شدن بخش اول، دوبله پخش می‌شود؛ پیشرفت دوبله مستقل از دانلود پیش می‌رود (پخش از روی ترجمه انجام‌شده).
- نوار کنترل: Play/Pause، Skip ±۱۰ ثانیه، سرعت 0.75/1/1.25/1.5، متوقف کامل.
- خروج از تب/بستن کروم → دفعه بعد «Continue Episode» از همان نقطه ادامه می‌دهد (پیشرفت در storage).
- پنل متن (اختیاری، جمع‌شدنی): متن اصلی + ترجمه به‌صورت دوستونه با اسکرول هم‌زمان.

### ۵.۳ الزامات عملکردی
1. **یافتن منبع صوتی:** تشخیص `audio`/`video` در صفحه → `currentSrc`؛ اگر چند مورد → انتخاب کاربر (لیست کوچک). منابع blob/مسیر مستقیم از content به SW ارسال شوند.
2. **دانلود قطعه‌ای:** SW فایل صوتی را به‌صورت range-chunk (۲۰–۳۰ ثانیه) می‌گیرد (`fetch` با host permission)؛ **کل فایل در حافظه نگهداری نشود** (فقط بافر قطعه فعلی + بعدی).
3. **ASR زنجیره‌ای:** رونویسی قطعه به قطعه با کانتکست (ترجمه ۲–۳ قطعه قبلی در پرامپت) برای ثبات اصطلاحات؛ خطای قطعه → تلاش مجدد ۲ بار → skip با ثبت در گزارش.
4. **ترجمه:** `translateItems` با onProgress؛ **تأخیر پخش مجاز است تا وقتی ترجمه جلوتر از پخش است**؛ اگر ترجمه عقب افتاد → مکث خودکار + نشانگر «Buffering…».
5. **سنتز:** صف TTS فاز ۳؛ تولید دوبله به‌صورت پیش‌فعال (prefetch) تا ۶۰ ثانیه جلوتر.
6. **پیشرفت و ادامه‌دهی:** کلید `podcastProgress` با `{ url, audioHash, positionSec, speed }` در chrome.storage؛ تحديث در pause/unload/هر ۱۰ ثانیه؛ «Continue» فقط اگر url+hash یکسان.
7. **رونوشت (transcript):** فقط در حافظه + کش متن storage (متن نه صوت)؛ قابلیت Copy.
8. **محدودیت:** اپیزود تا ۲ ساعت؛ بیش از آن پیام «Episode too long».

### ۵.۴ معماری
```
content: detect audio src ──▶ SW ──fetch range──▶ audio chunks
SW: ASR(chunk) → translateItems → synthesizeSpeech → queue
offscreen: play queue + speed + progress events
storage: podcastProgress {url, hash, positionSec}
```

### ۵.۵ تست
- **واحد:** range-fetch mock (Content-Range)؛ منطق پیشروی/پس‌افتادگی ترجمه؛ ادامه‌دهی (hash mismatch → شروع نو)؛ محدودیت ۲ ساعت؛ parsing انتخاب منبع.
- **واقعی:** یک فایل صوتی فارسی/انگلیسی محلی یا صفحه پادکست واقعی → Dub Episode → پخش، Skip، سرعت، بستن و Continue.

### ۵.۶ معیارهای پذیرش
- [ ] پخش از ترجمه آماده‌شده، نه منتظر کل اپیزود
- [ ] Continue پس از بستن کروم از همان ثانیه (hash معتبر)
- [ ] ترجمه عقب‌افتاده → مکث شفاف «Buffering» بدون قطع
- [ ] هیچ فایل صوتی‌ای در storage نمی‌ماند

### ۵.۷ خارج از محدوده
پلی‌لیست/فید RSS، دانلود دوبله، حالت آفلاین، تنظیم پیش‌فرض سرعت.

## ۶. فاز ۶ — تعویض خودکار صدا بر اساس گوینده

### ۶.۱ هدف
در دوبله ویدیو/پادکست (فاز ۴/۵)، هر گوینده با **صدای مجزای ثابت فارسی** دوبله شود، به‌صورت خودکار.

### ۶.۲ رویکرد (پیشنهاد) و گزینه‌ها
- **الف (پیشنهاد): برچسب گوینده در ASR + صدای هر گوینده از صف موجود.** پرامپت ASR: «Prefix each turn with Speaker 1/2/…». Segments → گروه‌بندی → نگاشت ترتیبی گوینده‌ها به صداها (اولین ظهور = Speaker 1 → Kore، 2 → Puck، 3 → Charon، …). سنتز همان صف فاز ۳ با voice منتخب per جمله. ساده، با همه‌چیز موجود جور است.
- **ب: multiSpeakerVoiceConfig در یک درخواست Gemini** (برچسب `speaker` + voice در TTS API تأییدشده در docs). مناسب فاز ۵ (متن کامل موجود)؛ دقت بیشتر یکپارچگی لحن؛ اما هم‌زمانی/خطای یک درخواست کل بخش را می‌شکند و طول درخواست محدود. → به‌عنوان بهینه‌سازی فاز ۶ نگه داشته می‌شود، در فاز ۵ پیاده نمی‌شود.
- **ج: پیش‌گذر دیاریزاسیون جداگانه.** هزینه + تأخیر اضافه؛ فقط اگر دقت الف برای گفتگوی هم‌پوشان ناکافی بود (تصمیم بر اساس تست واقعی؛ معیار: تشخیص درست ≥ ۸۰٪ گوینده‌ها در فیکسچر دوگوینده).

### ۶.۳ داستان کاربر
- در پادکست گفتگویی، هر گوینده با صدای متفاوت و ثابت شنیده می‌شود؛ ترتیب صداها ثابت (همیشه مبلّغ = Kore اگر اول باشد).
- Settings → Voices: نگاشت خودکار پیش‌فرض؛ کاربر می‌تواند برای هر Speaker دستی صدا عوض کند (Dropdown صداهای پیش‌ساخته)؛ «Reset».
- در Dub tab بدج تعداد گوینده‌های شناسایی‌شده («۲ speakers»).

### ۶.۴ الزامات عملکردی
1. **پارسر سگمنت:** خروجی ASR را به `{speakerId, text, startSec}` تجزیه کند (نسبت به متن پیوسته) — با regex سخت‌گیرانه + fallback به تک‌گوینده.
2. **نگاشت پایدار:** نگاشت به ترتیب اولین ظهور؛ در ذخیره `speakerVoiceMap` (storage) با کلید hash منبع؛ هرگز در طول یک جلسه تغییر نکند.
3. **کتابخانه صداها:** حداقل ۸ صدای پیش‌ساخته پشتیبانی‌شده (`Kore, Puck, Charon, Aoede, Fenrir, Leda, Orbit, Zephyr`)؛ بررسی طبیعی‌بودن فارسی هر صدا در تست واقعی فاز ۶ و حذف صداهای ضعیف (معیار: نظر کاربر).
4. **یکپارچگی با فاز ۴:** در حالت Live، تغییرات گوینده به‌صورت لحظه‌ای اعمال (هر خوشه برچسب دارد)؛ جابه‌جایی صدا در وسط جریان مجاز و روان (بدون کلیک).
5. **خطا:** سگمنت بدون برچسب → صدا پیش‌فرض؛ بیش از ۴ گوینده → ۵+ همان صدای ۴ (با اطلاع در Settings).

### ۶.۵ تست
- **واحد:** پارسر برچسب‌ها (انواع پرامپت/فارسی/انگلیسی/هم‌پوشانی)؛ پایداری نگاشت بین جلسات؛ override و Reset؛ fallback تک‌گوینده.
- **واقعی:** فیکسچر صوتی دوگوینده → دوبله با دو صدای متمایز ثابت؛ تغییر دستی voice در Settings و تأثیر آن در پخش بعدی.

### ۶.۶ معیارهای پذیرش
- [ ] دو صدای متمایز و ثابت در طول اپیزود؛ نگاشت یکسان در پخش مجدد
- [ ] override دستی ذخیره و اعمال می‌شود
- [ ] هیچ رگرسیونی در فازهای ۱–۵ (تست کامل)

### ۶.۷ خارج از محدوده
شناسایی گوینده به‌نام (diarization هویتی)، بازسازی لحن گوینده (voice cloning — ممنوع به‌دلیل خط‌مشی Google)، چندصدایی در فاز ۳ (Read Page).

## ۷. وابستگی‌ها، نقاط عطف و ریسک‌ها

### ۷.۱ وابستگی فازها
- فاز ۳ ← نیازمند فاز ۲ (صف/پایپ‌لاین) — در حال ساخت
- فاز ۴ ← نیازمند فاز ۲ (دیکدر استریم بعداً جایگزین صف می‌شود: رابط صف حفظ شود)، tabCapture (permission جدید: **در مانیفست اضافه شود**)، اسپک فاز ۴ (جداگانه، پیش از شروع — مطابق رویه brainstorming)

| ریسک | احتمال | اثر | کاهش |
|---|---|---|---|
| تأخیر پروکسی → دوبله زنده بالاتر از ۲.۵ ثانیه | متوسط | تجربه ضعیف | خوشه‌بندی کوتاه‌تر، Streaming TTS اولویت، نمایش تأخیر |

- دوبله زنده: ضریب «درست شنیده شدن» ≥ ۸۰٪ جملات بدون خطای ترجمه فاحش (نظرسنجی ساده کاربر در تست واقعی).

- چندگوینده: ثبات صدا در کل اپیزود و بین دو اجرای پیاپی.

## ۹. ضمیمه — نکات فنی API (تأییدشده در docs، ۲۰۲۶-۰۸)
- **TTS:** `POST /v1beta/models/gemini-3.1-flash-tts-preview:generateContent` با `generationConfig.responseModalities:["AUDIO"]` + `speechConfig.voiceConfig.prebuiltVoiceConfig.voiceName`؛ خروجی `candidates[0].content.parts[0].inlineData.data` = base64 PCM (24kHz، 16bit، mono — `audio/l16`؛ باید هدر WAV ساخته شود). استریم: `streamGenerateContent` (فقط 3.1+). کانتکست ۳۲K توکن؛ بدون caching؛ چندگوینده با `multiSpeakerVoiceConfig.speakerVoiceConfigs[{speaker, voiceConfig}]`.
- **Live Translate:** خروجی گفتار→گفتار؛ ورودی PCM 16kHz (خوشه‌های ۱۰۰ms)، خروجی 24kHz؛ نیازمند ephemeral token سرور (v1alpha) — خارج از محدوده.
- **هشدارهای TTS:** خطاهای تصادفی token (retry)؛ رد پرامپت مبهم توسط classifier (به پرامپت پیموده شده در فاز ۳ رجوع شود).
- **قوانین پروژه:** تست واقعی الزامی؛ refresh دستی پس از build؛ پروکسی `127.0.0.1:10808`؛ کلید فقط در storage محلی.
